## Context

当前任务步骤的轮询模式（`iterate_all`）总是从匹配到的第一个可见元素开始依次处理。当页面成员较多、任务曾因异常中断、或用户只想从某个偏移继续时，缺乏指定起始位置的能力，导致前 N 个元素被重复点击或无效等待。

本变更在步骤编辑表单中新增「从第几个元素开始轮询」数字输入框，数据模型新增 `iterate_start_index`（默认 1）。执行引擎在原地轮询和裂变轮询两条路径中均需遵守该偏移：扫描可见元素后，先跳过前 `startIndex - 1` 个，从第 `startIndex` 个开始点击；进度统计以实际可处理的元素总数为分母，但日志中的点击序号反映全局位置（如 `轮询 [6/14]`）。

## Goals / Non-Goals

**Goals:**
- 用户在 UI 可设置轮询起始偏移，默认从第 1 个元素开始。
- 起始偏移同时支持原地轮询（`iterateInPlace`）和裂变轮询（`runFanoutStep`）。
- 旧任务无 `iterate_start_index` 字段时，行为与默认 1 完全一致，保持向后兼容。

**Non-Goals:**
- 支持负偏移、倒数第 N 个、或从指定文本/ID 开始（超出本次范围）。
- 改变现有的分批、裂变、确认框、点击下钻等既有逻辑，仅在其之前增加跳过逻辑。

## Decisions

**1. 偏移语义采用 1-based 索引**
- 用户输入「1」表示从第一个元素开始，符合中文直觉。
- 内部计算时 `skip = startIndex - 1`。

**2. 起始偏移在扫描可见元素后生效**
- 先由 DOM 选择器获得可见元素有序列表，再按顺序跳过前 `skip` 个；未被跳过的元素仍按原有逐元素流程处理。
- 这样分批/全局计数从第一个实际处理的元素开始重新计数，避免用户因跳过导致第一批数量对不齐。

**3. 进度总量仍使用总可见元素数**
- `addProgressTotal(totalVisible)` 保持不变，ETA 估算仍基于完整列表；实际只处理 `totalVisible - skip` 个，进度条会在 100% 前停止，但这与 ETA 的「预计总时间」一致，避免偏移设置后 ETA 显得过短。
- 日志中的 `clickedCount` 反映实际已处理的元素个数（从 1 开始），分母 `totalVisible` 保持不变，便于用户对照页面。

**4. 输入校验：仅允许正整数，非法值回退到 1**
- UI 使用 `type="number" min="1"`。
- 执行引擎保存时取 `Math.max(1, parseInt(...))`，空/0/负数统一按 1 处理。

**5. UI 显隐：仅在勾选「轮询页面所有相同元素」时显示**
- 输入框放在「轮询间隔（秒）」上方；未勾选轮询时隐藏，避免干扰非轮询步骤。

## Risks / Trade-offs

- **Risk**: 用户设置的起始偏移大于实际可见元素数量，导致没有任何元素被处理。
  - **Mitigation**: 执行引擎在扫描后判断 `skip >= totalVisible` 时记录 warn 并跳过轮询，任务不中断。
- **Risk**: 页面 DOM 顺序与期望不一致，跳过偏移后点错元素。
  - **Mitigation**: 保持原有按 DOM/选择器顺序遍历的语义；用户可通过日志中的文本描述核对实际点击元素。
- **Trade-off**: 进度条分母使用 `totalVisible` 而非 `totalVisible - skip`，任务结束时进度不会到达 100%。
  - **理由**: 保持 ETA 估算稳定，且用户可以通过日志看到「从第 N 个开始」的处理过程。
